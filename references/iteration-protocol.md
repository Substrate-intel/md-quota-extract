# 迭代协议：skill 自我迭代 + 版本管理 + 跨用户回流（v1.0）

> 目标：每一次用本 skill 完成一卷提取，skill 本身必须变得更好；
> 任何使用者的迭代都能以受控质量回流，而不是只在本地各自漂移。

## 一、强制回写清单（每卷门控全绿收官后执行，属于收官动作的一部分）

完成一卷后，**必须**按以下顺序回写（禁止"用完就走"）：

| # | 回写对象 | 触发条件 | 动作 |
|---|---|---|---|
| 1 | `references/pitfalls.md` | 本卷踩了新坑（清单之外的形态） | 追加新坑：**症状→根因→根治→验证证据**四件套，编号续接 |
| 2 | `references/volume_params.md` | 本卷发现新的硬编码形态 | 追加到替换点地图；属通用形态的同步追加 check_volume_params.py CHECKS |
| 3 | `references/pipeline.md` | 出现阶段级差异 | 更新对应阶段，注明来源卷 |
| 4 | `scripts/check_volume_params.py` | 发现新的"漏改会静默错配"特征 | 追加 CHECKS（本卷实测值验证过再入） |
| 5 | `scripts/*.py` | 本卷产生可复用的结构性改进（**非卷特有逻辑**） | 回写参考实现；卷特有逻辑只入文档，禁入通用脚本 |
| 6 | `CHANGELOG.md` | 上述任一回写发生 | bump 版本 + 记录 |

## 二、迭代质量门槛（三件准入制，禁止只记症状）

一个新坑/新检查项要回写进 skill，必须同时具备：

1. **根因**：结构层根因，不是表象复述；
2. **根治**：可复用的修法，**不能是"下次注意"式口头纪律**——凡可通过机械手段防住的（扫描器检查项、断言、门控），必须落成机械手段；
3. **验证证据**：本卷已跑过门控/复现验证的数字口径记录。未经本卷验证的只能写"待验证"并注明。

**禁止入清单**：只在本卷出现一次且无复用可能的细节；带敏感路径/个人信息的内容。

## 三、版本管理（git + 语义化版本 + tag）

- skill 目录即 git 仓库；版本号 `vMAJOR.MINOR.PATCH`：
  - PATCH：文档修订、pitfalls 补充不改结构；
  - MINOR：新增检查项、新坑入库、脚本兼容性改进；
  - MAJOR：管线阶段结构变化、脚本接口不兼容变更；
- 每次回写：`git commit`（消息格式 `MINOR: +坑12 XXX形态（卷名）`）→ `git tag vX.Y.Z`。

## 四、跨用户回流协议

**使用者迭代流程**：
1. 获取 skill（zip 或 git）→ 正常完成一卷；
2. 按强制回写清单迭代 → bump 版本 + CHANGELOG 记录（每条含来源标识：`- 来源: <标识/卷名> · <联系方式或仓库>`）；
3. 回流二选一：
   - **git 路径**（推荐）：fork 仓库 → 提交迭代 → 发 PR/MR；
   - **zip 路径**：重新打包发回作者（附 CHANGELOG diff）。

**作者审核门槛**（合并前必查）：
- [ ] 每条变更过了三件准入制？
- [ ] 卷特有逻辑没有混进通用脚本？（抽查 scripts/ diff）
- [ ] 新 CHECKS 项验证过不误伤？
- [ ] 版本号 bump 符合语义化？
- 未过审：打回并注明缺哪件；过审 → 合并 → tag → 发新版包。

**注意**：skill 自带的回流脚本只做标准 `git push origin main`——推送到使用者本机配置的 remote。fork 使用者推自己的 fork（对上游仓库无写权限，直推 403），不会污染上游。

## 五、防漂移守卫

- 基准卷参数 + 扫描器比对 → 使用者改没改、改得干不干净，**机械可验**；
- 版本号 + CHANGELOG → 演进历史**可追溯**；
- 回流必须带证据 → 迭代质量**有门槛**；
- 作者审核 checklist → 合并权收敛，**不会出现两个互不相认的"官方版"**。
