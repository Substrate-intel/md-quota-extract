# 坑全清单（基准卷 lvse 实证，症状→根因→根治→验证四件套）

> 编号 1-17；坑 1-11 与 docx-quota-extract 坑 25-34 同源（lvse 提炼），坑 12-17 来自 sz11 第二卷实战（2026-10-15）。

## 一、转换层（阶段 0）

### 坑 1｜pymupdf4llm import 即段错误
- **症状**：`import pymupdf4llm` 段错误（exit 139，1.28.2 layout 引擎）。
- **根因**：布局引擎 C 库与运行环境冲突（pymupdf 本体不受影响）。
- **根治**：转换层用裸 fitz 自研（字号分级 + find_tables）。
- **验证**：269 页全转，md 字节级可复现。

### 坑 2｜旋转水印 redact = 整页抹除
- **症状**：对 ~40° 旋转水印行 bbox 做 redact → 整页内容塌缩。
- **根因**：旋转文本 bbox 是旋转外接矩形，轴对齐化后罩全页。
- **根治**：不 redact；单元格级**行首**孤立 token 剔除 `^([水印字符集])\s`——行首锚定防「基价」等双面字误伤。
- **验证**：水印字符零泄漏进表行；「基 价(元)」等正常术语无损。

### 坑 3｜E-BZ 页码散字：单字符行 + 外侧边 + 分区 offset
- **症状**：页码提取 0 命中或数字倒序（'942'≠'249'）。
- **根因**：西文嵌入字体基线下沉致页码每字符独立成行；位置在**外侧边**（偶页左 x≈50、奇页右 x≈510），居中假设错误；目录区与正文区 offset 不同。
- **根治**：y 带 + 外侧边 x 双条件收集散字，**按 x 左→右重组**（禁 reverse）；offset 分区标定；无页码扉页对排除。
- **验证**：页锚 258/269；扉页对（12/13、66/67…）正确排除。

## 二、md 解析层（阶段 1-2）

### 坑 4｜章标题 `# ` 前缀剥离 → startswith("#") 判界静默全失效
- **症状**：册说明 buf 吞掉 848 段落；所有文本前缀判界静默失效（不报错、产物悄悄错）。
- **根因**：extract_md 产块时剥掉 md 标题前缀存 text，下游沿用文本前缀判界。
- **根治**：块结构显式 `kind:"h1"/"h2"`，**全部边界检查改 kind 判定**。
- **验证**：册说明段落收敛至权威条数；章节区间全对。

### 坑 5｜md 合并单元格形态 ≠ docx 纵向合并
- **症状**：消耗行分类失败（kind 链断裂）；名称行/消耗行混淆；跨列标签留空。
- **根因**：docx 纵向合并读出**每行重复值**，md 合并单元格**只有首格有值**——两种 Office 形态语义不同。
- **根治**：行判别三法——①消耗行=c0 空+前 kind 链式；②名称行=r[1] 无值+r[3:] 非数字文本；③跨列标签 hfill 横向填充；费用行 `"(元)" in joined`；规格/档位行放行。
- **验证**：487 子目 parse_issues=0，人材机消耗行全分类。

### 坑 6｜工作内容/计量单位拆行 → 双遍扫描
- **症状**：430 子目 unit 空（单遍扫到「工作内容」行即 break）。
- **根因**：docx 两者同段，md 拆成独立两行，单遍状态机被先出现的行截断。
- **根治**：unit/work 各扫一遍；分号结尾的「N.」子行是工作内容延续**不 break**。
- **验证**：unit/work 零空（门3 全绿）。

## 三、目录/条文层（阶段 7）

### 坑 7｜目录双栏重组（不经 md）
- **症状**：目录行错配/丢行/页码错挂。
- **根因**：双栏排版全文序输出左右栏交错；md 表格化破坏字符坐标。
- **根治**：从 nowm.pdf 目录页 dict 直接重建——x 分栏 + 栏内 y±6.5 聚类 + 长标题/页码行合并；页码字符坐标是唯一权威。
- **验证**：目录 N 行与正文集合全等、页码单调（门6）。

### 坑 8｜节标题折行污染 sections → 跟表验证
- **症状**：sections 32 个 vs 目录权威 14 个。
- **根因**：说明区长标题折行后恰命中节标题正则。
- **根治**：节标题判定加**跟表验证**（其后 6 块内须有表格）；窗口必须 6 块（4 块漏表距 5 块的案例）。
- **验证**：sections 与目录节行集合全等。

## 四、校验/前端层（阶段 6/9）

### 坑 9｜H1 恒等式项数因卷而异
- **症状**：H1 全卷 fail（曾 487/487 红）。
- **根因**：沿用三项式（基价=人+材+机），本卷实为**四项制含综合费**。
- **根治**：H1 公式**开工前用已知好卷样例校准**；「—」费项按 0 计并留痕；H2 费率带宽按卷实测。
- **验证**：H1 487/487（299 条「—」计 0 留痕）。

### 坑 10｜P1 灵活正则必须作用于未去空白原文
- **症状**：P1 44/487 fail——去空白后相邻编码粘连 '20-920-10'，lookbehind 误杀。
- **根因**：页文本 strip 后相邻子目编码拼接；E-BZ 数字间距又被随机空格拆开——两个方向同时破坏正则。
- **根治**：正则作用于**原始未去空白**页文本：编码 `(?<!\d)前缀-\s*N(?!\d)`、基价 `120[\s.]*78`（E-BZ 空格容忍）。
- **验证**：P1 487/487（对**官方带水印原版**取证——提取用 nowm 干净源、校验用官方原版，双源口径）。

### 坑 11｜前端契约错配致「加载中」假死 + 冒烟必须渲染级
- **症状**：成果库首页永远「加载中…」；文件存在、门控全绿（基线锚的就是错配版）。
- **根因**：两级——①build_front 产出 docx 短键契约 DATA，模板吃 PDF 长键契约（`DATA.stats.h`/`DATA.sections.some` 相继 TypeError，script 整体崩溃）；②冒烟只验文件存在未执行渲染。
- **根治**：①严格按 PDF 长键契约组装 DATA（见 pipeline 阶段 9 契约清单）；②渲染级冒烟机械化（smoke_front.mjs：启动链+13 视图路由真跑）。
- **验证**：冒烟 22/22；端到端字节级一致；九门 9/9。
- **纪律**：前端完成态=渲染级冒烟全绿；门控基线只锚「可复现」不锚「可渲染」。

## 五、流程纪律（管理类）

### 坑 12｜水印 Form XObject：删指令级（sz11 实证，坑 2 的根治升级）
- **症状**：字符级 redact 去水印必误伤（水印字符 bbox 与正文重叠，sz11 P11 目录页实证 `(52)→(52`、整行被抹）。
- **根因**：本批次官方 PDF（lvse/sz11 同源）的旋转水印封装在**独立 Form XObject**（如 Fm0，内容流仅 `/SimHei 36 Tf` + 单 Tj），主内容流仅一条 `/Fm0 Do` 引用。
- **根治**：`re.sub(rb"/Fm0\s+Do\s*", b"", cs)` 删指令=**物理隔离零误伤**；逐页对账（删除前后非旋转文本字节级一致，任一页不一致即中止）+ 全书终验残留=0。
- **验证**：sz11 245/245 页零误伤。**比坑 2 的"行首 token 剔除"更优**——有 XObject 形态优先走本坑，无 XObject 才退坑 2。

### 坑 13｜章码≠章序 + 章码重复 + 目录/正文章码不一致（sz11 实证）
- **症状**：①二三四章**共用 041102**；②第六章目录印 041105、正文印 041106；③按章码字符串匹配节行 → 断链（22 子目无 node_id）。
- **根因**：官方排印的章码是"编码体系位"不是"序号位"——重复/错位是书印事实，且目录与正文各自印刷可能不一致。
- **根治**：①章判别逐章**物理锚定**（按 h1 块位置切，禁按章码聚合）；②**节行按「目录章序」归章**（章行依序出现=序号 1..N，建立 order→章 code 映射），禁章码字符串匹配；③排印不一致留痕进 issues 不静默修正。
- **验证**：sz11 470 子目全部归属（44 节点）；门6 节名 ⊆ 目录节行全等。

### 坑 14｜书印无「工作内容」行 → 门3 断言语义（sz11 实证，**曾误诊为 SEC_RE 截断**）
- **症状**：work 空 18 条。曾误判为「表前『N. 名称』行被 SEC_RE 截断」——修正 SEC_RE 前后数字**不变**，证明非真因（回溯先遇「工作内容」段即 break，根本到不了名称行）。真因：**书印即无**（临时建筑/混凝土外加剂等组从「计量单位」直接进表）。
- **根治**：①定性靠证据——抽查缺work子目的 md 原文上下文，书印无该行=事实（留痕，不硬造，坑 20 同源精神）；②门3 断言改为本卷实测值+口径注释（`n_work == 18` 带「书印事实」说明）；③抽查脚本字段名先对 schema（items.json 是 list+字段 `work`，用错字段名会造出"全缺"假象——sz11 实证乌龙）。
- **验证**：18 条全部书印无该行（md 原文逐条目检）；门3 PASS 带留痕口径。

### 坑 15｜换参机械化的三类系统性漏网（sz11 实证，**积分消耗大头**）
- **症状**：换参后首跑连环炸——CODE_RE 漏换（codes 空）、三处路径漏换（Downloads/out_md 逐个 FileNotFoundError）、smoke 路由假绿（12001→041101 语义错位）。
- **根因**：①映射表写 `r"20-\\d{1,3}"` 双反斜杠形态，文件里是单反斜杠字面量 `20-\d{1,3}`——**永不命中且不报错**；②映射只换文件名不换目录（Downloads/nowm.pdf）；③**短码体系**（章码[2:] 如 041101→1101）在换参时被当全码映射（12001→041101），冒烟路由渲染空页也 PASS=假绿。
- **根治（机械手段，防"下次注意"）**：新增 `scripts/preflight_check.py` 开工自检——路径存在性全查、编码/章码正则对 md 源试命中（0 命中即红）、章码[2:]短码路由核对、守卫集成跑一遍、断言占位扫描。**换参后先跑 preflight 再进管线**，把 10+ 轮调试往返压到 1 轮。
- **验证**：sz11 复盘——三类漏网均可在 preflight 一轮内暴露。

### 坑 16｜页码带/单位白名单先实测再定参（sz11 实证）
- **症状**：页码 y 带 340-375 搬 lvse 参数首跑 0 命中（sz11 页码 y=350.4 精确）；H5 白名单三轮才补齐（漏 10台次/台次，再漏 10个）。
- **根治**：①页码标定**先抽样打印页脚 y 分布**再定带（禁直接搬上卷参数）；②H5 前先 dump 全库 unit 分布，一次性补齐本卷单位全集（措施项目特性：台·天/座·天/架次/次/10延长米堰体/100m3空间体积/10t金属设备 等）。
- **验证**：sz11 终态 H5 fail=0、页码三区段恒定 offset+13。

### 坑 17｜finalize 嵌核验数字 → 顺序依赖（sz11 实证）
- **症状**：端到端重跑后 db 字节失配；单跑 finalize 三连测却稳定。
- **根因**：finalize 嵌入 cost_check_report 的动态数字（H5 白名单修正期间核验数字在变）——db 内容依赖上游核验报告版本。
- **根治**：收官固定顺序 **finalize→cost_check→（参数变更后）再 finalize**→build_front；或 finalize 不嵌核验中间态。
- **验证**：固定顺序后九门全绿+复现验证通过。

### 坑 36｜窄表编码在 r[1] → 宽表搜索漏抓整表（az09 实证）
- **症状**：解析层报「无定额编号行」，措施项目类子目（9-282~286）整表消失，后续编号断档。
- **根因**：单/双子目窄表仅 2-3 列，编码在第 2 列 r[1]（清单编号/项目名称合并列），原代码行搜索只扫 r[3:]（宽表形态假设）。
- **根治**：代码行搜索加窄表回退——`len(r) > 1 and CODE_RE.match(cellname(r[1]))` 即认定（清单编号行不会匹配 9-N 全码形态，无误伤）。
- **验证**：az09 9-1~9-286 连续 0 issues。

### 坑 37｜视觉行左右分块 → 纯 y 排序颠倒（az09 实证）
- **症状**：19 条 work 截断 + 3 条缺单位（9-207/208/209），表现零散无规律。
- **根因**：convert 层纯按 y 稳定排序，但同一视觉行的左右分块 y0 相差 ~1.1pt（P26 实证：左「…水压试验、水」y=46.7 / 右「计量单位:10m」y=55.7 与「冲洗。」y=56.8 同视觉行），右段（续行/单位行）被插到左段与下一行之间，阅读顺序颠倒。
- **根治**：convert 元素排序改视觉行聚簇——y 差 ≤3pt 聚为同簇、簇内按 x 排序（正常行距 ≥10pt 不受影响）。
- **验证**：work 截断 0、缺单位 0。

### 坑 38｜计量单位挂续行尾部（az09 实证）

- **验证**：az09 单位缺失 0（与坑37 叠加根治）。

### 坑 39｜目录缺章标题行 → 全章下级行错挂（az09 实证）
- **症状**：前端节点树 ch2 无节、ch1 混入 ch2 节；子目章归属整体偏移。

- **验证**：az09 目录 101 行、6 章归属性 0 错挂；第二章子目 47 条全部回位。

### 坑 40｜附录标记误触 → 全书子目表变附表（az09 实证）
- **症状**：附表组首跑 0 条；放宽检测后二跑 53 条（全误）——P20 之后所有子目表被判附表。

### 坑 41｜章无「一、」式节行 → 回退其他行构造节节点（az09 实证）
- **症状**：冒烟「N 子目全部有 node_id 归属」fail——5 条系数计取项（9-282~286）无节点，前端树中不可达。

- **验证**：冒烟 24/24，节点 48→49，286 子目全归属。

## 六、流程纪律（管理类）

- 校核≠重做；疑点留痕不静默；subprocess 三件套（capture_output+stdin=DEVNULL+timeout）。
- 每卷门控全绿后**强制回写本 skill**（iteration-protocol.md），禁"用完就走"。
- **双源 sha12 锚定先实测后写死**（az09 实证）：换参脚本 MAP 注入的 sha12 若凭记忆填写，会同时污染 gate ANCHORS / build_front 数据串 / cost_check 文档串，且产物已生成后难以察觉。正确做法：文件就位后先 `sha256sum` 取前 12 位，再回填各锚点；official_wm.pdf 应与用户原始下载件字节级一致（可 `sha256sum` 溯源闭合）。
- **换参后全链 grep 卷名/前缀/短码三类残留**：az09 收尾曾抓到 smoke_front 4 处 sz11 残留（layer:0913:fb 路由/11-10 弹窗/11-1 断言×2/「含 11 章」硬编码）、build_front title「0411」、注释「本册统一 11-」——占位符 token 回填只覆盖数字，卷名/路由/标题类残留必须单独全链扫。

### 坑 42｜mupdf save 随机写 trailer /ID → nowm.pdf 字节漂移（sz02 实证）

- **根因二（逆序页码逐字成行）**：`get_text("dict")` 里页脚每个数字是**独立 line/span**（P27：`'1'@x56.1` 与 `'0'@x60.6` 两个 line，真值 10）。按"行文本必须是纯数字"匹配，每行只取到一个数字，拼接顺序还依赖行序。
- **根治（四条件同时成立）**：
  1. y 阈值降到 **0.85H**：覆盖横版小页（0.867），同时仍高于正文表格下沿（正文页实测 0.908）；
  2. **页缘条件**（`x0 < 0.20W` 或 `x1 > 0.80W`）排除表格中部数字；全页无页缘候选时才退回全局；
  3. 同 y 簇（±2pt）**跨行合并**候选后按 x 排序拼接（坑52 逆序存储的机械化实现）；
  4. 取 **y 最大**（最底部）簇，而不是原实现的 `cands.sort()[0]`（最小 y）——表格数字行恒在页脚之上，取最小 y 会在表格拖到底部时误取。
- **教训**：门控报"失配"先分清是**数据错**还是**读数错**。用 `page.get_text()` 打印该页底部所有候选（含 x/y/y/H）比改断言快得多。单点阈值（0.85/0.89）永远脆弱，形态判据 + 页缘 + 簇合并三重约束才稳。

### 坑 128｜修复未回写模板 = 跨卷带病复制（gy 8-2999 漏解实证，2026-11-20）

- **现象**：gy 门1 报 `parse_issues=1`（`{"tbl": 854, "issue": "无定额编号行"}`），parse 得 2998 项而 md 编码全集是 **8-1~8-2999 连续 2999 个**，差的正是册末「其他项目·措施项目」的 8-2999 脚手架搭拆费。
- **根因**：坑121 的「编号行全列扫描」当时只落在 xtx/tf/yb 三卷，**没回写 jz，也没回写模板**。gy 以 jz 为模板换参，原样带回 `for c in r[3:]`——两列「标签｜值」表（`清单编号 001005 / 定额编号 8-2999 / 项目 脚手架搭拆费`）的编号在第 2 列，`r[3:]` 永远扫不到，整表被跳过。
- **根治**：编号行检测改全列 `for c in r`（`CODE_RE` 为 `^<pref>-\d{1,4}$`，不会与 6 位清单编号或档位值混）；改后 2999 项、issues=0，与 md 编码全集精确吻合。
- **纪律（本轮最贵的一课）**：任一门控/解析修复必须**当场回写模板与最近验证卷**，否则下一次复制就是带病复制；`parse_issues` 不为 0 时先追问"少了几项"，用「md 编码全集 vs DB 编码全集」做集合差，比逐表排查快且必中。

### 坑 129｜单位形态用枚举正则 = 必漏（20 卷「见表」专项，2026-11-20）

- **现象**：全库扫 `unit like '%见表%'`，20 卷 1236 格。表面看是「原书印见表」，实际打开原书单位行，绝大多数**印着清清楚楚的真单位**，只是形态不在枚举里。
- **根因**：`UNIT_ROW_RE = ^(?:\d{1,3})?(?:m2|m3|m|…|延长米)$` 是**固定枚举**。实测被它判否的真单位有 19 种：`百条`、`台(部)`、`端口`、`芯`、`百线`、`架`、`子架`、`一个口`、`10线`、`10头`、`套.天`、`套·天`、`半周长m`、`100m3空间体积`、`每增4点`、`1000个`、`节/12m`、`吨`、`次/端面`。判否 → 回落成「见表」。
- **根治**：改为**判定器**（`_UnitCellMatcher.match()`，调用点签名不变）：
  1. 去空白后 ≤12 字；
  2. **纯数字否决**——`80/120/180` 是规格行残留，不是单位；
  3. **规格词否决**——`以下/以内/以外/以上/≤/＜/＞/30X30X5/1:2`，防名称行误入；
  4. 含**单位令牌**（中文单位字 + 拉丁单位符 + 复合单位后缀）。
- **纪律**：单位形态永远不要枚举穷举，枚举即漏；「令牌白名单 + 否决词 + 长度/纯数字护栏」才是收敛解。白名单（`cost_check.UNIT_OK`）只加**逐格取证**得到的形态，绝不按数据全集回填——那样门5 就失去意义。

### 坑 130｜OCR twin 链单位全空的双根因（xj10~xj15 1112 格实证，2026-11-20）

- **根因一（同行粘连）**：原书把工作内容与计量单位印在**同一行**——`…直管安装等操作过程。计量单位：100m`。`WORK_RE = ^工作内容[：:](.*)$` 整行吞掉尾段并 `continue`，`cur_unit` 永远是空（xj13 全书 142 子目单位全空、xj12 312 空）。**xj15 早年已用 `strip_inline_unit` 修过，但没回写其余 5 卷**——坑128「修复未回写=带病复制」的又一例，且这次跨的是**另一条管线（OCR 链）**。
- **根因二（单位行混入项目组）**：本项目族把计量单位印成表内**单独一行**（`| | | 10m3 | | | 10根 |`）。OCR 分块按「编号行」切块，该行落在编号行与「名称」表头之间，被 `proj_rows` 收走当项目名 → 单位成了名称尾巴（xj11 `凿除桩顶钢筋混凝土 打入桩 10m3`），子目 unit 仍是「见表」。
- **根治**：① `strip_inline_unit` 移植 6 卷（`INLINE_UNIT_RE` 行尾匹配，剥离后回填 `cur_unit`）；② `parse_item_block` 内识别**纯单位行**（该行所有非空格都通过判定器 → 从 `proj_rows` 剔除，用 `assign()` 按列归属到 `unit_by_code`）；③ `close_tbl` 取值优先级：`cur_unit`（且非「见表」）> 块内行单位 > `blk["unit"]`。
- **结果**：xj10 155→8、xj11 402→14、xj12 337→4、xj13 142→**0**、xj14 50→6、xj15 26→4；余 36 条为**源表该列单位格空白**（合并格起点不明）或 OCR 字形噪声（`七`←`t`），按「疑点进 issues 禁静默修正」留痕。
- **顺带教训**：**xj15 的管线顺序是 `parse_fee → build_db → apply_errata → build_front`**。漏 `apply_errata` 会同时报两个假象：门2「items 少 4」（补充子目没插入）与 `sqlite3.OperationalError: no such table: erratas`（门10 读不到表）。看到这两个一起出现，先查 errata 跑没跑。

### 坑 131｜dict 键类型混用，静默返回 None（xj11 单卷 402→14 的关键一修，2026-11-20）

- **现象**：坑130 的补丁打完后，xj11 的 402 格只降到 368，且**名称尾巴的单位确实被摘掉了**（说明纯单位行识别生效），但 `unit` 仍是「见表」。无异常、无告警。
- **根因**：`parse_item_block` 里是 `for c, code in codes`——`c` 是**列号(int)**、`code` 是**编号串(str)**。按列建的 `unit_by_code` 是 int 键，取值处写成 `unit_by_code.get(code)`，字符串键永远取不到 → `None` → 回落「见表」。改成 `get(c)` 后 402→14。
- **纪律**：凡「以列号作 dict 键」的地方，取值处逐个核对键类型；**静默 `None` 比抛异常贵得多**——它不打断流程，只在最终数据里留一片空白，且会被误判成"源书就是没有"。

### 坑 132｜单位格判定：结构定位置、尾字定形态（OCR 链 6 卷实证，2026-11-20）

- **现象（两类反向错误，都是坑130 补丁的副作用）**：
  1. **项目组标题被当单位**：xj11 `3-1-1` → `unit=陆上工作平台`、`name=≤2500`；xj14 `8-1-42` → `unit=复合地基 桩径600mm内`。
  2. **项目名被整行吞掉**：xj10 空名 80 条、xj11 33、xj12 14、xj14 19、xj15 9——单位行吸收把唯一那行项目名吃掉，名称变空。比原问题更隐蔽：`unit` 看着有值，`name` 空了。
- **根因**：单位格判定用「含单位令牌」松判据，而 `口/台/块/架/子/线` 等单字单位大量出现在项目名里（洞口/平台/块石/门架/绝缘子/管线）；吸收行时又**自顶向下**扫，先撞上的是项目组标题行。
- **根治（五条，缺一不可）**：
  1. **自底向上吸收**——原书单位行紧贴「名称/单位/消耗量」表头，从 `proj_rows` 末尾往前，遇第一个不合格行即停；
  2. **保名门** `while _k > 1`——至少留一行当项目名，单位行不可能吃掉全部项目行；
  3. **表头门**——`计量单位：X` 已印真单位（非「见表」）时，表内行不再抢位（`blk["_hdr_unit"]`）；
  4. **尾字定案**——纯中文且**不以单位令牌结尾**一律否决（`浆砌块石`/`户外式支持绝缘子`/`加固处理` 全灭）；规格词扩展 `深度|覆土|厚度|宽度|高度|长度|直径|容量|重量|间距|跨度|层数|桩径|井深|内$`；
  5. **名称尾单位只拆数字开头的**——`10根`/`10m3`/`套·天` 可拆，纯汉字尾（`金属杆座`/`避雷器 组`）**不拆**。实测反例：xj15 `B5-17` 名称「三表计量与远程 传输系统」被拆成 `unit=传输系统`，连带勘误 E02（B5-16~20 台→系统）整组失配、门10 报「非法状态 issue」。
- **战果**（见表/空单位 ; 空名称）：xj10 8/1;30、xj11 13/3;0、xj12 8/0;0、xj14 1/0;0、xj15 5/0;0、xj13 0/0;0。全库「见表」1236 → 38。
- **纪律**：单位格判定不能只靠「令牌包含」——**结构定位置（自底向上 + 表头门）+ 尾字定形态（否决 + 数字前缀）**才是收敛解。名称与单位同源时，宁可单位留「见表」，也不能拆名——拆名是静默篡改，`见表` 是可核的留痕。

### 坑 133｜横向合并格丢格/错位：竖线断续=几何权威 + ⟪lo:hi⟫ 标记 + 表头单位优先（xj10 专项，2026-11-20）

- **现象（30 条空名称只是冰山一角）**：xj10 间隔 6 的组首空名（1-1-71/77/83…243）+ 组名错挂（74 错拿「20m以内 四类土」）+ 规格当单位（10-2-47 `unit='二线'`）+ 档位被拆（`加固孔深 10m` → `unit=10m` 丢「孔」）。看似四个病，同一源形态：**横向合并格（组名跨列居中）+ OCR 列漂移**。
- **三处根因（缺一即复发）**：
  1. **convert sec_cells 误拆**：「一、二类土」以「一、」开头被节标题正则整格拆出表格 → 组首列丢土类变空名。修复分型：**中文序数 sec 与表内数据同行 → 整行回表格**；数字型 sec（工作内容续行「2.松填土…」）必须保留拆出——parse 层 `work_open` 拼接依赖它，一刀切会回退（实测：工作内容续行整段丢失）。
  2. **合并格跨列信息丢失**：组名居中只归位中心列，左列缺名 + span 推断溢铺相邻组。根治链：convert `extract_grid` 保留**竖线 y 段区间** → 合并单元格处竖线断开 = 跨列合并边界（几何权威，bbox 覆盖法不可靠——居中文字 bbox 不满格）→ 行内分段（gap>6pt）+ 段两侧最近「存在竖线」定 [lo,hi) → md 输出 `⟪lo:hi:text⟫` 标记（lo/hi=网格列 index，md 表格 cell 内）→ parse 端 `CELL_SPAN_RE` 解释：标记优先精确铺到 code_cols∈[lo,hi)，裸 cell 的 span 右界遇标记 cell **截到其 lo**（否则「一、二类土」(71列) 会溢铺进 72 列）。
  3. **规格档位误当单位**：a)「二线/四线/六线」被令牌「线」误判 → `_is_unit_cell` 否决 `[一二三四五六七八九]线|\d线`（「百线」是合法单位，百不在单字表，不误伤）；b) `_TAIL_UNIT_RE` 在表头已印真单位时仍拆名称尾档位 → **`_hdr_authoritative` 门**：表头单位（`blk["unit"]`，注意 `cur_unit` 在单位行印于表格 buf 内时恒空，须 `cur_unit or blk.get("unit")` 兜底）非空非「见表」时不拆。
- **战果**：空名 30→0、规格当单位 10→0、消耗不同同名对 90+→4（余 4 为 ocr.pdf 源级 span 连读，无矢量可切，留痕+原书取证不臆改）；1-1-71~243 推土机/铲运机/挖掘机 29 组全部「机型+推距+土类」完整归位；10-2-47~52 =「一端埋设式 二线」unit='根'。
- **smoke 守护断言**（防回退）：空名=0、规格词不得当单位、1-1-71 归位、10-2-47 归位——同时废除「写死疑点总条数 384」断言（坑133 修复后 issues 结构变化，写死条数违反「canonical 单源」纪律）。
- **连带纪律**：`md` 表格统一网格是**全页所有表竖线的并集**——不同表的假列界会让 ⟪lo:hi⟫ 跨多列，只要 code_cols 在范围内唯一即无伤；parse 数值行遇标记按范围归位，范围含多 code 才退回最近列。

### 坑 134｜OCR twin 链「同名不同消耗」：档位行拼入名称的五处断链（xj11/12/14/15，2026-11-20）

- **现象**：52 对相邻子目「名称完全相同、消耗量却不同」（xj11 35 / xj12 8 / xj14 7 / xj15 2）。典型如 `墩台(高度≤m)`（5m/10m/15m 三档同名）、`公设直径(mm以内) DN1500 mm以外` 与 `DN1500` 同名、`送桩φ600钢筋混凝土管桩送桩φ800钢筋混凝土管桩`（两列连读）。
- **业务危害**：使用者查到「墩台(高度≤m)」不知是 5m 还是 15m 档，单价差 30%+；「同名不同量」是造价套用最危险的形态（选错档位直接错价）。
- **五处断链（缺一即复发）**：
  1. **表头单位断链**：`blk["_hdr_unit"] = cur_unit` 少了 `or blk.get("unit")`。当「计量单位：10m3」印在**表格 buf 内**时页面级 `cur_unit` 恒空 → `_need_ur=True` → 底部档位行（5m/10m/15m，`_is_unit_cell` 认「m」）被当单位吸收。这是坑132 在 OCR 链的漏网（只回写了 xj10）。
  2. **单位优先序错**：`_u = unit_by_code.get(c, "")` 未接表头单位 → 空的 `_u` 触发 `_TAIL_UNIT_RE` 尾部拆分，把刚拼进名称的档位又拆走当单位（`墩台(高度≤m) 5m` → 名称退回缺档态、unit=5m）。正确序：**表头单位 > 块内单位行 > 名称尾拆分**。
  3. **归位按 span 溢铺**：`if lo <= c < hi` 在空列漂移时把单值铺到多列（P33 `φ609.60`@5 溢出到 108、P36 `φ≤1600`@8 落到 134 之外）。改为代数对齐四分支：
     - `K == N`（非空格数=编号列数）→ **顺序镜像**（原书横向严格一一对应，最强判据）
     - `1 < K < N 且 N % K == 0` → 等分覆盖，但**值必须落在自己那一段内**（否则是右半区独立档位，P62 水泥掺量会被错铺到左半区）
     - `K == 1` → 规格形态恒单列（`mm以外`）；项目行内且无全宽档位行→单列（P86）；否则整表组名（P30 管桩、P36 入岩增加费）
     - 其余 → **最近列、平局取右**（P30 `φ1000`@11 距离 10/12 相等，取右才对 84）
  4. **名称连读**（OCR 把相邻几列名称读成一个 span）：按需切分 + 等分铺列。切分证据强弱两档：**相邻段最长公共子串 ≥4 字**（`方桩送桩L≤32m`/`方桩送桩L≤40m` 共享 8 字；`送桩φ600…`/`送桩φ800…` 共享 7 字）；**数字+厚度单位边界**（`防水橡胶板2mm` + `聚氨酯防水涂料`）。切分入口三处：整表同名 / 块内连续同名 / 有名列向左右吸收空名段。切不动就**回填最长名 + `name_inherit` 留痕**（空名比带邻居信息的待核名更不可用）。
  5. **名称仅剩档位 / 空档占位**：组名行未覆盖该列时名只剩 `≤1000` → 补同块**首个**组名前缀（取最长会串到别的组，实测把矩形阀门的名字贴给圆形）；原书印 `墩台(高度≤m)` 这类空档模板（档位值在下一行）→ 用档位值填占位 `墩台(高度≤5m)`。
- **战果**：52 对 → **2 对**（xj11 3-6-9/3-6-10「滑板底板×模板」、4-2-23/4-2-24「模板台车×挡头模板」，均属「部位×工序」二维表头，相邻值列距与合并宽度无代数对应，留在 `name_inherit` 留痕待人工）；空名 0；四卷门控 9/9、9/9、9/9、10/10 + 二跑 MATCH + 回流 12/12。
- **纪律**：门9 已知类型表须同步登记新 kind（`name_concat_split` / `name_inherit` / `name_prefix_fill` / `name_grade_inline`），否则报 unknown_kinds；`_is_grade_val`（档位判别）必须排除表头词——「公称直径(mm以内)」含 mm/以内 但是量名不是档位值，误判会把整表组名压成单列。
- 工具链：`sp/_ln_gap/patch_name_grade.py`、`patch_grade_span.py`、`rebuild_ocr.py`。

### 坑 135｜名称只有尺寸串 / 跨块跨节同名：原书组标题行是唯一可用组名（xj12，2026-11-21）

- **现象**：坑134 收口后 xj12 仍有两类「名称不可检索」：

  1. `name_caption_prefix`（223 条）：`split_blocks` 增设 `capctx`「当前组标题」记忆，识别**表格内单格、带 `(N)/N./N、` 前缀、≥4 汉字**的行 → 不入行流，挂给后续块；`parse_item_block` 末尾判「整块名称汉字 <3」→ 补 `组标题 + 名称`。`capctx` 必须**跨表格缓冲区存续**（组标题行与编号行常被一条非表格行「工作内容：…」隔断成两个 buf），章/册扉页清零。

### 坑 138｜专项计价依据（管廊/传统建筑/绿色建筑）正本子目提取（子坑 1–12，2026-11-23）

**背景**：广东 6 项专项依据（轨交/管廊/传统建筑/绿色建筑/工期）此前只登记来源。本轮从平台公开电子书下载 13 件 / 3013 页，管廊 1563、传统建筑 2266、绿色建筑 189 共 **4018 子目 / 27145 明细行**结构化入库，平台侧复算守恒 0 例外。三册版式互不相同，踩坑集中如下。

1. **章/节标题不能取「表头上方最近一行」**：那一级是**子目组**（`1 人工挖一般土方`、`(1) 打预制方桩`），**序号在本节内重置**，当章号必错（实证 `G1.4 → 地槽内打桩支架`、`W1.2 → 1 地面拆除`）。正解按**标题编号段数**判级：两段号 `G.1.2 地基处理及基坑支护工程`＝章，三段号 `G.1.2.1 地基处理`＝节。三册规则不同——管廊/传统建筑用字母编号，绿色建筑用 `第N章` + `N.M`。

2. **绿色建筑的 `N.M` 必须卡字号**：正文与表格里大量 `1.1`、`3.2` 这类数值会冒充节号，不卡字号首版扫出 **1188 条假节**（真值 51）。章 `第N章` 取 `size≥17`、节 `N.M` 取 `13≤size<15`。

3. **章名要「目录页 ∪ 正文页」两路取全**：`G.1.3 桩基础工程`、`W.1.3 传统木作工程`、`G.2.6 智能化系统设备安装工程` **只在目录页印全**，正文首页版式未印章标题；只扫正文会缺章、导致该章子目挂到上一章。目录页只供名表、不给位置（位置取正文页标题）。

4. **目录页判定用「正文起点」而非点线**：正文本页＝首页出现「定额编号」表头的页，之前整页按名表处理。依赖 `·`/`…` 点线判目录不可靠——部分目录行点线被拆成独立 span/行，`is_toc` 判不出来。

5. **子目挂章按 (file, page, 纵坐标)**，章标题缺失时由节号回推（`G.1.3.1` → `G.1.3`）并从名表补名。结果 4018/4018 命中、**章号与子目码互检 0 处不符**（该互检必做：`expect_chapter()` 由码解出应有章号，与挂接结果比对，不符即报，不静默）。

6. **`name_groups` 列尾回填会压掉合并单元格的名称**：组尾按「下一组 start−1」回填时，若两组同 start（合并格组 + 普通组），前一组被顶成 `end < start`，`range(start, end+1)` 为空 → **整段名称静默丢弃**（绿色建筑 5-3-1~4 名称变 `设备重量(t) 单价`）。修：只有 `key is None`（无竖线可依）才回填，且 `end = max(end, start)`。

7. **判表头不能比整行文本**：竖排「分/类」与「单价」会挤在同一行（`jt='分单价'`），整行比对漏网 → 该行当名称。改「整行每个 span 都是表头词」才判表头。

8. **判表头时绝不能顺手置 `head_y`**（子坑 7 的连带雷）：费用行解析全部套在 `if head_y is None` 守卫内，一旦提前置位，后续费用行**全部跳过、五要素整片丢失**（隧道 G1 从 1563 掉到 1010）。判表头只 `continue`，不动 `head_y`。

9. **字母资源码的分类不能用位置继承**：分类列是竖排居中的合并格，每种资源块**首条常落在标签之上**而错继承「人工」→ 金额按数量算（`Ljc05001` 聚烯烃管 102×10.05 被算成 10.05，少 1015；3-7-1 少 26198）。改为按码制/单位/名称判：单位 `台班`→机具、名称「人工费」→人工、其余→材料（保留既有「机具」标记）。数字码仍按位数（`0001` 开头 8 位=人工、≥9 位=机具、其余=材料）。

10. **单位与费用标签的两种写法**：单位有 `计量单位：台` 与 `单位：10m` 两套（绿色建筑 5-7-4 用后者），只匹配「计量单位」会漏；费用标签有裸写 `机械费`（无「(元)」），未映射则机具费为空、基价恒等式直接失败。

11. **符号字体的私有区字形**：`CIDFont+F3` 用 PUA 画复合符号且无 ToUnicode——`U+E000`→`m³`（全书 588 次，渲染比对确认）、`U+E002`→`mm²`（BV-1.5 电缆规格）。另有 `≤O.5` 的字母 O 实为数字 0（内嵌字体 0 画成 O 形），仅按 `(?<=[≤≥<>])[Oo](?=[\d.])` 归一，不做全局替换（`DN100` 的 O 不能动）。

12. **原书自身缺陷：一律不改数，只做标记**（这是定调，不是建议）。原书自己的重号与印价矛盾**不许替编者修正**——改了就无法反查「哪几条与原书不一致」。两类问题：
    - **重号**：绿色建筑 p77 三列印成 `6-6-7 / 6-6-7 / 6-6-8`、次页自 `6-6-10` 起，按码序应为 `6-6-7 / 6-6-8 / 6-6-9`（疑误印）。**不改码**，两条均按原印码认定；后一条入库码加 `-2` **仅因主键硬约束**（平台 `id=uuid5("costing://<lib>/<code>")`，同码必 `duplicate key` 整批回滚），备注须点明「检索与对外引用仍视为原码」。
    - **印价不守恒**：`5-3-1`~`5-3-4` 基价 1257.45 而 919.27+16.49+16.35+269.36＝1221.47（差 35.98；另三条 31.60/45.33/81.08），据消耗明细反推机具费应为 52.33（919.66×0.050＋64.83×0.100＝52.46）与基价吻合 → 判原书机具费印错。**不改价**：五费照印录入，消耗明细不写入（写了就与人材机三费自相矛盾），反推值只写进说明、**不进任何价格列**。
    
    **标记两层，缺一不可**：
    - **tags**：`原书疑误` + 类型（`重号`/`印价不守恒`）+ `待核定` + `未改数`。**重号的两条都要打**——只打加后缀那条，按「重号」检索只能查到一半（本项首发即踩）。
    - **备注**：`note_type='orig_issue'` 单立一条（`note_id` 用 `ISSUE-<卷>`），与来源备注 `special_source` **分离**，平台侧可按类型一次筛全，不必全文检索；正文写原书页码、实测数值、差额、反推值与「照录未改」结论。
    
    **幂等**：事务开头 `DELETE FROM quota_library_item_notes WHERE library_id=? AND note_type='orig_issue'` 再重插，否则某条不再标记时留下孤儿说明。实测二灌后子目 189 / 疑误 6 / `orig_issue` 备注 6 / 三表行数全不变。

**口径边界（不补造，写进交付物）**：轨交**土建 5 册**（354 页）是总说明/章节说明/措施费/规费/管理费分摊费率表，全册**无一处定额编号**，属「费用与规则册」不是子目册；轨交**安装 2 册**（350 页）纯扫描件（仅封面有文本层），须 OCR 另立专项；**工期定额 2022**（368 页）是工期表，与「子目—五要素—消耗明细」不同模型，不并入子目库。

**工程纪律**：`g1`（基价＝人工+材料+机具+管理）、`g2`（明细合计＝人材机三费，容差 1.5）双门禁逐条判定，**g2 不过的子目只入五要素不写明细**；入库只 INSERT `quota_library_items`（含 `resource_composition`）由触发器分发三表，**禁显式写三表**（双写翻倍）；二灌幂等用「按 tags 删本脚本写入的子目 + 按章码删本章」实现，重跑后子目/备注/三表行数完全不变。

### 坑 139｜矢量转曲「规则汇编」PDF 的 OCR 与规则库结构化（子坑 1–10，2026-11-24）

**背景**：广东轨交安装 2 册（350 页，实为第六册通信 + 第七册信号 + 第八册供电 + 第九册智能与控制系统安装**四册**合订）此前判为「纯扫描件待 OCR」。本轮实测推翻：它们是**文字转曲的矢量 PDF**，且是官方发布的**「说明与规则汇编」**——通篇册说明、章说明、工程量计算规则、措施项目、其他项目、税金、附录，**不含一张子目表**。OCR 后按「册—部分—节—块」四级把规则文本与参考表结构化入库。

1. **载体定性三件套，别把「转曲」当「扫描」**：`get_text()` 为空、目录页文本层乱码（字体无 ToUnicode，读出来是 `!!!" ~-!:F&'`）**不等于扫描件**。判据：`get_drawings()` 有大量矢量路径、`get_images()` 覆盖率低、渲染 200dpi 边缘锐利无噪点 → 文字转曲矢量 PDF，无需去噪/纠偏，直接用 200dpi 渲染喂 OCR。

2. **「无子目表」可能是载体本身没有，不是解析失败**：判据是**原书页码成对跳页**——第六册印页 `17→19→43→45→77→79→107→109…`，每章「说明页/计算规则页」相邻成对，中间整段被略去；PDF 149 页而末页原书印到 333。结论：这是按原书页码抽页重编的规则汇编，子目表页从未收录。**报告口径必须改成实测结论**，不能沿用「扫描件待 OCR」这种含糊说法。

3. **多进程/单进程的取舍要按实测，不要凭直觉**：本机 4 核，单进程 ≈5–23 s/页（目录页块密、正文页快），3 个进程并行净吞吐约 10 s/页。配套**分页落盘 + 存在即跳过**（`<page:03d>.json`），中断可续跑、可多进程分range跑而不互相覆盖——`_ocr_page` 落盘前再查一次存在性，重叠 range 也不会重复劳动。

4. **同一视觉行的碎块必须按 x 重排再拼**：目录表里名称块常比编号块高 1–2 点，按 OCR 返回顺序拼会把编号拼到行尾（`挖、填光（电）缆沟及敷设通信管道M. 6. 1`），章名就取不到。分组容差 5pt、组内按 x0 排序。拼接口还要按边界字符决定补不补空格：CJK/数字相邻不补，否则出「之和的 39. 35%」。

5. **章名以目录为准，但目录本身要先洗**：章扉页大字号标题常被 PDF 切成 2–3 个 run，OCR 在断口丢偏旁（`缆`→`纟`，实证 M.6.1「挖、填光（电）**纟**缆沟」），目录行是单 run、干净。但目录也会脏：原书印「环境与机电设备监控系统（BAS）」，OCR 把**全角左括号认成大写 E**（`…系统E(BAS)`），不洗就把 E 读进章名。清洗三件套——去空格、半角括号转全角、剥掉括号前的单个西文字母；洗完再比对，只差括号全半角的不记账，52 章里实质不一致只剩 2 处（M.6.1 丢偏旁、M.9.6 扉页「电子信号机房」vs 目录「电子信息机房工程」，属**原书自身两处印得不一致**），按目录取正、扉页原文照记（`toc_diff` 落 JSON）。

6. **条目编号正则的 `\s*` 会吃掉前瞻**：`^(\d+)\s*[.．]\s*(?!\d)` 对「1. 50%计算。」仍判成条目——`\s*` 回溯后前瞻只看到空格就通过。正解把空白写进前瞻：`[.．](?!\s*\d)`。不改则费率句被切碎（「…按专业工程造价的」与「1.50%计算。」两条）。另：**「式中/其中/注：」要自成一段**，否则赶工公式与 `式中，0.80≤δ<1.00` 粘成一行。

7. **压平小表必须视觉转写，且正文由同一份数据生成**：合并单元格表 OCR 会压成一行、丢列，甚至列序错位——「名称省级文明工地市级文明工地 / 1.002.00文明工地增加费率（%）」照字面读会把省级读成 1.00（实为市级 1.00、省级 2.00）。做法：视觉读图转写成 `rows`，再用**同一份 rows** 生成一句正文（`表：X —— 甲 1.00；乙 2.00。`）替换压平行，保证「表里一套、文中一套」不会发生；表体跨多行时用 start/end 锚点整段删除，**锚点未命中必须报错**不静默。视觉核对过的字符也要留痕（δ 被 OCR 认成 8、`×` 认成 `X`、`≤` 认成 `<`），改动写进 normalizize 日志。

8. **册界三条线索，缺一条就整册错挂**：不能只认「整页 ≤3 行且首行是第X册」的册扉页——第八册开头没有扉页（第 2 页就是目录，页眉印「第八册 供电工程」），第九册、第十册更狠：**连扉页和「总说明」标题页都没有**，只有册说明首句「…《广东省城市轨道交通工程综合定额》第九册《智能与控制系统安装工程》（以下简称本册定额）」。正解按可靠性排序：①册说明首段的「第X册《…》」（册名齐全）；②**总说明首条「一、《广东省城市轨道交通工程综合定额》…」的起点**——这是册说明之前那段规则群的真正起点，缺它则本该属于本册的总说明会被上一条界吞掉；③册扉页兜底。最终册界取「本册说明之前最近的②」，否则③，否则册说明页本身。另：目录页眉、册扉页、册说明三处会重复报到同一册，`new_vol` 必须按册号幂等，否则建出空壳册。

9. **表头型锚点要连锚点一起删，引导句型锚点只能剔表头**：视觉转写表的定位锚点有两种性质，混用必留脏行——①锚点本身是表头（`序号 专业册 计算基础 管理费分摊费率（%）`）→ 整行删；②锚点是引导句（`1.光缆预留量规定见下表：`）→ 保留句子，但 OCR 常把表头粘进这句（`…见下表：序号项目预留长度（m）`），必须按 `strip_re` 剔掉尾巴。判据用表名即可（`管理费分摊` 前缀为表头型）。同页还有一处坑：**告警要在 OCR 原文上判**——若在正字/视觉修正之后再判，被修好的问题会判成「已解决」，反过来若页面已视觉转写了表而引导句还留着旧告警，就得在处理时显式 `pop("_suspect")` 关闭它，否则永远不会清零。

10. **章起始印页只能从目录拿**：章扉页整页只有「M.6.1 / 章名」两行，**不印页码**，靠页脚取页码会全空。目录里章标题行本身也不带页码，页码挂在紧随其后的「说明……953」上——所以目录解析要维护「当前章」状态，遇到第一个带尾部数字的行就记为该章起始印页。

**战果（2026-11-24）**：上册 149 页（第六册通信 16 章、第七册信号 8 章）+ 下册 201 页（第八册供电 15 章、第九册智能与控制系统安装 6 章、第十册机电设备安装 7 章）**五册合计 350 页 / 52 章**全量 OCR；落平台四表——章目录 52 条（章名后缀「规则章·无子目表」）、册级说明 808 段/45 块（总说明/册说明/措施项目/其他项目/税金/附录）、章级说明 586 段（说明 298 + 工程量计算规则 288）、参考表 19 张 1357 行（5 张绿色施工构成表各 259 行 + 光缆/电缆预留量 + 施工环境与条件调整系数 + 彩色摄像机折算系数 + 五册各一张工程优质费表与管理费分摊费率表 29.44/29.44/28.74/30.66/39.86）。二灌 md5 一致、该库原有 90 条补充子目未动、待核 10 条全关闭。**口径纪律**：OCR 认错字按原书图像核对修正并留痕，**原书自己的数一个不动**。

### 坑 140｜分类标签只在合并格首行 → 整类资源放错抽屉，而守恒门禁"总数平"照样放行（广东专项三库，2026-11-24）

**现象**：平台专项三库（管廊 1 563、传统 2 266）共 908 个子目的台班消耗行（挖掘机、液压锤、压路机）挂在**材料明细表**里，材料费虚高、机具费虚低。典型 `W1-6-42 型钢栏杆`：材料多 1 070.42、机具少 1 070.43，**分毫不差**——不是金额算错，是整类资源放错抽屉。

**三个根因，缺一不可**：

1. **原书消耗量表的「人工/材料/机械」是合并单元格，只在每组首行印一次，续行不重印**。解析时没做「承上」，18 873 行类别为空。合并格标签还有个陷阱：它印在**单元格的垂直正中**，不是首行——`机械` 组跨 182.5~242.5 三行，标签落在 212.5，且常与资源码粘成一串（`机械990401015`）。所以**不能按标签 y 就近归组**，用相邻标签 y 的中点切带也会错（本例中点正好压在第一行边界上，且大组会被切走一半）。
2. **导入脚本对空类别静默兜底**：`TYPE.get(c["cat"], "material")` 把空类别全塞材料表。正解是**空类别/未知类别直接抛错**，宁可中断也不兜底。
3. **门禁太松掩盖了它**：当时的守恒门禁只比「全部明细合计 = 人+材+机三项之和」——不分类别，台班挪进材料表后总数照样平，门禁零例外放行。正解是**逐类守恒**（人工明细合计 = 人工费、材料 = 材料费、机具 = 机具费），同一份数据立刻暴露 908 条。

**分类判定的可靠次序**（不要靠标签 y）：资源码 `0001` 开头 = 人工（单位「元」、单价印「-」、金额 = 消耗量）；单位「台班」= 机械；其余 = 材料。判完再用「每个同类连续组的 y 区间内必须存在同名合并格标签」做独立互检（标签词表 `机具↔机械` 要映射，否则全组误报）。

**平台侧只许定点重写**：子目表上挂 `quota_item_embeddings`（AI 匹配向量，级联删除），**删了重灌会把向量清空**。用 `set_item_composition(item_id, jsonb)` 重写三表，写前先全表备份、写后按「只允许分类/名称不同，编码/单价/消耗量/金额任何差异即拒绝」做安全闸（本轮 4 028 子目里 1 237 条需重写、2 877 行改类别、353 行去名称粘连，材料 21 617→18 740、机具 1 555→4 432，行数分毫不差）。

### 坑 141｜「见表」单位要按表线切格取，不能按列中心±距离硬取；PUA 字形要按码位实测（广东专项三库，2026-11-24）

**版式事实**：专项定额表里单位独占一行，夹在**名称块最后一行与「基价(元)」行之间**；有的子目一列一个单位格，有的是**一格横跨几列**（`10m²` 管 4 列）。此时按「列中心 ± 固定距离」取会拿到邻列文字，按「基价行上方最后一个文本行」取会把规格残字带进来。

**正解三步**：① 定额编号行按 x 排序得列中心；② 在基价数字行上方（`fy-22 ~ fy-3`）取单位行，**在该行 y 上用竖向表线切出单元格**；③ 每列取「落在本列格内」的文字（合并格自动跨列）。本轮 381 条见表单位，378 条自动取到、3 条目视确认（`组日`、`点次`、`部`、`m/三轴`、`每10m高`、`100元` 都是原书照印，别当噪声删）。

**两个附带坑**：

1. **表线不是 `l` 操作符**：PDF 里表格线是 0.4pt 宽的**填充矩形**（`get_drawings()` 全返回 `re`，宽度 <1.6pt、高度 >4pt）。按 `it[0]=="l"` 找竖线会一条都取不到，误判成"单位格内无文字"。
2. **PUA 私有区字形要扫全量码位、别信终端显示**：终端里 `\ue000` 打印出来是空白，容易被当成"空串"而漏映射。扫全部页面的 `U+E000~U+F8FF` 建频次表，本书只有两种（`\ue000→m³`、`\ue002→mm²`），映射无歧义。清 PUA 时要**同时清三个字段**：子目长名称（`name_full`）、**短名称（`quota_name`）**、明细行名称——本轮只清了长名称，平台侧短名称残留 55 条方块字。
3. **纯数字单位是"图形符号没被提取"**：绿色建筑指引的 `100 ㎡` 面积符号是矢量图形，文本层只剩 `100`。别猜（卫生器具那一节同样是 `10`，实际是 `10 组`、LED 灯是 `10 套`）——**表头「计量单位：…」是可提取的文字，以它为准**（本轮 47 条：100㎡×32、10㎡×7、10 套×5、10 组×3）。

### 坑 142｜台班册「单独计算的费用」1/2/4/6 列窄表：写死列坐标必整片错位；表线切格 + 最近行锚点重建（广东 jtb 9913，2026-11-24）

**现象**：`9913 单独计算的费用`（大型机械安拆费，4 页 20 个子目）明细表出现「单位栏塞着台班单价」「编码栏写着『机械』二字」「首列消耗量整列丢失」「分类标签只在合并格首行」。表头五费是对的，明细全错。

**根因**：这 4 页**确实是定额子目表式**（不是台班价格表），但只有 1/2/4/6 列、列宽与常规子目表、台班表都不同。旧解析器写死了台班价格表的单位列/单价列坐标，套上去整片错位；再被「分类为空兜底成材料」放大（见坑 140）。

**做法**（与坑 141 同一技术路线，可复用）：

1. **列分界取表线**，别用固定坐标：在消耗区表头行下方 8pt 取竖向细矩形 → 得五条分界 `分类|编码`、`编码|名称`、`名称|单位`、`单位|单价`、`单价|消耗量`。**注意价格列右缘与首列消耗量左缘只差 4~5pt**（283.6 vs 288.1），用「编号列左缘 − 4」当分界比用价格列右缘稳。
2. **行锚点 = 资源码 span 的 y**；名称折行**按最近锚点归并**（名称常比编码行高/低各一行，如 `混凝土搅拌站` 在 anchor−5.6、`生产率45(m³/h)` 在 anchor+5.6）。用「±6.5pt 窗口」会漏三行名称，用最近锚点则任意行数都对。
3. **分类别信标签**：`0001` 开头 = 人工、单位「台班」= 机械、其余 = 材料，再用「每个同类连续组 y 区间内必须有同名合并格标签」互检。
4. **每个表块自带「单位：」行**（同页两块的单位可以不同：`单位：台次` 与 `单位：m（双轨）`），单位必须**按块取**，不能按页取。

**战果**：明细 114 行（人工 20 / 材料 38 / 机具 56），19 个子目逐类守恒、金额分毫不差（`991304004` 材料 606.38、机具 8 657.21 全中）；`991305008` 原书材料费印 129.76、明细合计 124.44，差 5.32，**照原书录入 + `原书疑误`/`印价不守恒` 标记 + `orig_issue` 备注**，不反推不改数。原平台 20 子目共 161 行（材料 45 + 机具 116，含大量错位空行），重写后幂等（内容指纹二跑一致）。

### 坑 143｜「台班 = 机械」是硬规则；门禁必须分类别、动态发现库、且要自证（广东全量复验，2026-11-24）

**业务口径**：台班册是**机械台班费用**的原始数据，与定额子目是两个不同层面的内容。所以「台班」这一类资源在任何库里**只允许进机具费**。进了材料费或人工费，就是整类资源放错抽屉——人材机三项合计照样平，但材料费虚高、机具费虚低、机械台班分析表取不到数、取费基数跟着偏。**这类错比金额错更隐蔽，因为任何只看总额的检查都发现不了。**

**硬判据（三条取并集，缺一不可）**：

1. 单位含「台班」（`btrim(unit) like '%台班%'`）——最直接，但会被「台班 15」这类粘了序号的脏单位绕过，所以还要第 2、3 条；
2. 资源码命中台班价格表（`resource_code in (select code from library_machine_prices)`）——跨库全量比对，最可靠；
3. 资源码形如 `^99\d{7}$`（广东台班码段 9 位 99 开头；材料码是 8 位，不会误伤）。

反向先不算错但必须 INFO 打出来给人核：机具表里单位不是「台班」的行（`元` = 其他机械费按金额计、`%` = 费率型机具、`t.d` = 吨·天），业务上合法。

**门禁三原则（上一轮踩过的三个坑，逐条对应）**：

1. **必须分类别，不能只比总额**。旧门禁比「全部明细合计 = 人+材+机三项之和」，台班塞进材料表总额照样平，门禁放行（管廊 731 行、传统 37 行就是这么漏的）。改成逐类守恒（人工 `sum(consumption)=人工费`、材料/机具 `sum(amount)=对应费`，容差 `greatest(1.5, 费×0.5%)`）才暴露。
2. **库清单必须按父库动态发现，禁止手抄 UUID 列表**。上一轮手抄 26 个 UUID，抄漏 C.6 整库（753 条子目）没进复核，却写成"全覆盖"。`select id from libraries where id='<父库>' or parent_id='<父库>'` 一行解决。父库本身 0 子目属正常（只作容器），别算成空库。
3. **门禁必须自证**：在**随后回滚的事务**里故意造错（把 2 条台班行塞进材料表、1 条塞进人工表），看门禁是否当场报数，`rollback` 后是否归零。不做这一步，"全绿"可能只是"没查"。——本轮实测：材料报 2、人工报 1、逐类守恒同步报 1，回滚归零。

**配套根治（比事后查更重要）**：导入器**禁止「未知类别 → 默认材料」的静默兜底**（`TYPE.get(cat,"material")` 这类写法），空类别一律 `raise`。上一轮 2 877 行错位就是「合并格标签只在首行 + 空类别兜底 + 门禁不分类」三者叠加。

**平台侧铁律**：三张明细表挂 `rebuild_composition_*` 触发器（AFTER INSERT/UPDATE/DELETE），改三表会自动重建 `resource_composition`。所以**改明细只走 `set_item_composition(item_id, jsonb)`**，它内部就是 DELETE 三表再 INSERT——触发器随后重投影，不需要手工维护组合字段。注意它只写三表、不直接写 `resource_composition`，别误以为写完函数就完事（要验证投影已变）。

**落地**：`scripts/gate_platform_gd18.py`（P1 库清单 / P2 投影一致 / P3 逐类守恒 / P4 台班归位 / P5 单位完整含 PUA / P6 编码唯一 / P7 规模对账），`--all` 可跨省复用。查「台班价格表重号」时注意**跨库同码不是重号**（`990803060` 在辽宁库与广东父库各一条，是两个省各自定价），判据必须带 `library_id` 分组。

### 坑 144｜「章树有章、章下 0 条」是最容易漏检的交付缺口；同卷混装数据要给检索对象切换（广东台班册，2026-11-24）

**现象**：站点章树里 `9913 单独计算的费用` 一直都在，点进去 **0 条子目**；册内搜编码、搜名称都搜不到塔吊安拆费与施工电梯安拆费。上一版报告把它写成「保留项：只在平台」，等于把一个空壳章交付出去了。

**根因三层**：
1. 本地 `items` 表从未收录这 21 条（20 条原书 9913 + 第 44 期补充 `补991305009`），只有平台台班库有 → 站点数据源就是本地库，所以查不到；
2. 前端台班视图写死 `VOL==='jxtb'`（只对辽宁独立台班卷生效），广东的台班费用表与子目**同在一卷**，永远走子目分支，1 614 条台班单价也查不到；
3. 门禁只查行数、守恒、单位、重号，**不查「章下有没有子目」**，所以全绿也发现不了。

**根治**：
- **数据侧**：以平台为唯一数据源回灌本地（`insert_jtb_9913_local.py`），字段按本卷既有规范（`vol=jtb`、`chapter_code=9913`、`print_page=PDF页+books.offset`、`source/period/doc_no` 标注期号与文号）；明细落 `item_consumes`（`cat` 中文、人工行 `qty`=金额、其余 `qty`=消耗量、`qty_br=1` ⇔ 未计价），三张站点投影表交给 `gd18_site_compat.py` 重建，**不要手写投影**。
- **前端侧**：给「检索对象」切换（定额子目 / 台班单价），显示条件是**三条与集**：`kind=quota` ∧ `counts.machines>0` ∧ `VOL!=='jxtb'`。默认仍是子目 → 不选台班时行为与改动前逐字一致，别的卷零影响；台班模式下隐藏章节下拉（该接口不吃 chapter 参数）。
- **门禁侧**：加一条「章下子目数 = 0 且该章在原书有子目」的检查，别让空章过门。

**两个易踩点**：
- 补充子目的 `补` 前缀是与平台对账的隐式主键，**必须与平台逐字一致**（`补991305009`），少一个字跨层对账就对不上；
- `volumes.json` 里的 `sha256/bytes/items` 会滞后于实盘（本项目实测注册表停在两版之前）。每次传库都要重算三字段，并把公开仓、私有仓、服务器三份对齐——**注册表 sha 与实际文件不符，等于指纹门禁失效**。

**验证要求**：不能只看接口返回条数，要在真实页面走一遍——切台班模式搜 `990304`（应出 22 条汽车吊单价）、切回子目看章节下拉恢复、`?vol=jxtb` 看老卷不出现切换。三个动作都过才算端到端。

### 坑 145｜定额库落库之后「能不能被业务系统用起来」是另一轮活：平台计算链三个会算错钱的坑（广东调用验证，2026-11-26）

**业务场景**：库落完了、门禁全绿，不等于能被造价平台调用。必须做一次「真建项目→真套子目→真执行计算→真看汇总」的端到端，否则「接口能通」只是通在纸面上。本轮真跑一遍，抓到三个都会直接算错钱的坑。

**坑 A：找不到资源用量时把「0 明细」当成「有明细」，用 0 覆盖综合单价并回写清零**

- 现象：清单行综合单价 1461.92，执行计算后库里变 0。
- 根因链：`findBillItemFeeDetail` 查 `resource_usages`（资源用量表）无记录时返回 `0/0/0`（不是 null）→ 引擎 `hasResourceDetail` 只判 null → 认为「有明细」→ 按 0 重算单价 → `updateBillItemPrice` 把 0 回写覆盖原值。
- 修法两层：取数三层回退（resource_usages → 清单行落库的 labor_fee/material_fee/machine_fee → 三费全 0 返回 null）；回写处加闸（算出 0 且原行单价 > 0 时跳过回写并 warn）。
- **通用教训**：任何「null 表示没有、0 表示有但是零」的语义，在金额链路上都要显式区分。回写型计算（把结果写回源表）必须带护栏，否则一次异常计算就把好数据毁了。

**坑 B：费率单位两套口径，税额差 100 倍**

- 现象：计算快照税 711.88，费用汇总表显示 7.1188。
- 根因：前端「费率(%)」列按百分比存（9 表示 9%），汇总服务除以 100（对），定价服务当小数 0.09 直接乘（错）。
- 修法：全平台统一**百分比存储**，消费端统一折算；缺省值也改成百分比字面量（5/3/0/9）保证折算前后等价。
- **通用教训**：费率字段必须在一处定义单位并写进注释与 DB 约束说明；同一个字段被两个服务读，就一定会分叉。

**坑 C：费率表全空，所有项目都在用代码里的硬默认**

- 现象：`fee_items` 整表 0 行；项目模板里配的 15%/8% 从未生效，实际一直用 5%/3%。
- 含义：模板字段（如 `managementFeeBase=LABOR_PLUS_MACHINE`）写好了但没人读，属于「配置了但没接线」。
- **通用教训**：验证「配置是否真生效」的方法只有一个——改配置，看结果变不变。本轮就是这么确认 ②③ 的：录 15%/8% 后单价从 1389.04 变 1581.96，证明链路是通的；再录 9 后税额与汇总表对齐，证明口径统一了。

**端到端验证的可复用手法**（不依赖前端登录）

1. 建临时会话：往 `user_sessions` 插一条 `token_hash = sha256('st_'+随机hex)`、`token_prefix` 取前 7 位、`user_agent='workbuddy-verify'`，即可用 `Authorization: Bearer st_xxx` 调所有接口；**事毕按 user_agent 删掉**。
2. 建项目 → 建单位工程（`POST /project-versions/{id}/unit-projects`）→ 批量清单行（`POST /unit-projects/{id}/bill-items/batch`）→ 执行计算（`POST /project-versions/{id}/calculate`）→ 取汇总（`GET /unit-projects/{id}/cost-summary`）。
3. **清单行类型必须是 `BILL`（父项）+ `QUOTA_LIB`（子项）**；用 `PART` 提交算不出数（`findBillItems` 只取 `parent_id is null and item_type='BILL'`）。
4. 校验三处必须一致：引擎返回的 `billItems[].unitPrice`、`summary.total`、`cost-summary.items[].amount`。三处不一致就是口径分叉。

**易踩点**：`fee_items.base_type` 有 check 约束，合法值只有 `FIXED_AMOUNT / TAB_SUM / PRE_TAX_SUM / FORMULA`；税金按「税前期合计」计取要用 `PRE_TAX_SUM`，用 `FIXED_AMOUNT` 会去取 `amount`（通常是 0）而显示 0 税。

### 坑 146｜取费口径定调后落地：后台「执行计算」必须与前端组价读同一个模板；定额自带管理费的省用「嵌入」而不是录费率（广东 V312，2026-11-26）

**业务场景**：费率口径定调之后（基数=人工+机械，可自行选择编辑；广东定额自带管理费，无需再定义广东费率），落地时发现前后端各算各的：前端组价读项目计价模板（`effectiveTemplate`：项目模板 ?? 系统「国标综合单价法」），后台「执行计算」却读规费表 + 硬默认 5%/3% + 基数人材机合计。同一个清单行两个入口算出两个价。

**坑 A：后台计算不读计价模板**

- 现象：广东项目按模板应为管理费 175.77（定额印刷值）/ 利润 233.264（20%×(人工+机械)），后台算成 192.92 / 102.89（15%/8%×人材机）。
- 修法：后台解析模板与前端同规则（项目模板优先 → 系统默认模板兜底 → 全都没有才走旧硬默认），费率、基数、嵌入开关都取模板；`fee_items` 里历史遗留的 MANAGEMENT/PROFIT/RISK 行**不再参与**（前端组价从不读它们，后台读就必然分叉）。
- **通用教训**：「同一业务口径在两个代码路径上分别实现」必然分叉。修法不是两边各自改对，而是让两边读**同一份配置**。

**坑 B：定额自带管理费的省，费率该留空而不是录数**

- 业务规则（爪哥定调）：广东 2018 各专业管理费是**逐子目不同的固定金额**（实测安装均值 31.5%、市政 20%、建筑装饰 17.1%，同库内还浮动），录统一费率必然错。利润才是统一率（轨交各册说明原文：以人工费与施工机具费之和为基础，20.00%）。
- 落地方式：挂系统模板「广东省2018（管理费嵌入）」——管理费 `managementFeeEmbedded=true`、费率留空；计算引擎在嵌入模式下直接取清单行落库的 `bill_items.management_fee`（套定额时从子目带入的印刷值），**费率即便非空也忽略**。
- **通用教训**：某项费用在数据层逐条固定时，配置层就别做「费率」这个概念；「嵌入」开关比录一列费率诚实。

**坑 C：兼容分支只服务于「不存在的数据」就是负债**

- 过程教训：第一版实现留了「规费页显式费率行覆盖模板」的兼容分支，实测立刻翻车——测试期手工插的 8% 利润行把模板 20% 压掉，而前端从不读这行。全平台只有测试插过这种数据，即该分支只对「我上一轮的测试痕迹」生效。删掉后口径归一。
- **通用教训**：兼容分支要问一句「现存哪些真实数据会走进来」；答不上来就删。

**验证方法（现网真跑）**：临时会话 → 按模板 A（国标）算一次 → 改项目模板为广东口径（PUT `/projects/{id}/pricing-templates/{id}`，同前端「管理费和利润」弹窗的保存链）→ 再算一次 → 两次结果分别手算对照 → 核三处一致（引擎返回 / `bill_items` 回写 / `cost-summary`）→ 服务端日志确认「计价模板生效 template=广东省2018（管理费嵌入）」→ 删临时会话与测试费率行。广东算例 A1-14-5×5：管理费 175.77 / 利润 233.264 / 单价 1 695.184 / 总造价 9 238.7528，三处一致，日志可溯。

### 坑 147｜恒等式审计的「条数」必须能被独立对象校验，否则 100% 通过也是假的（广东 A6 校正，2026-11-26）

**业务场景**：审计 A6 报「基价恒等式 24813/24813 (100.0%)」，看着完美。但拿它跟库里实际子目数（24800）一对，数差 13 条。逐条追下去发现三个独立缺陷，一虚两漏，恰好互相掩盖成一个小差数——**如果只看「100% 通过」这个结论，永远不会发现**。

**判据：审计的 `checked` 必须能对上另一个独立来源的计数**。对不上就说明口径本身错了，通过率再高也不作数。

**三个缺陷（都是「静默」型）**：

1. **虚增 +115｜配合比表被当成子目**。下册第 309–332 页「表3 预拌砂浆制作含量表」以「材料编号」为表头，是配合比表（m³ 材料配比），但它同样印「基价(元)/人工费(元)/材料费(元)/机具费(元)/管理费(元)」。只按「有没有基价标签」筛页，就会把 41 页 82 张配合比表当子目核算——而且这些表恒等式自洽，**加进来全是绿的**，总数被悄悄抬高。
   - 修法：按**表头**判型，不按标签判型。有「定额编号」= 子目表；有「材料编号」= 配合比表，跳过并单列 `skipped_mix_*` 计数。
2. **漏算 −12｜一行多值**。PDF 把同排多个数字抽成空格分隔的单行：`基价(元)` 下面是 `11109.73 13364.43 14440.48 15699.34` / 换行 `5631.47`。逐行 `^\d+\.\d+$` 匹配不上这一行，只拿到最后一个值 ⇒ 6 列只收到 1 个 ⇒ 列数不等 ⇒ **整页 `continue` 丢掉**。
   - 修法：值列逐 token 拆（`all(NUM.fullmatch(t) for t in line.split())` 则整行展开）。凡是「按行数取列」的解析器都要防这一手。
3. **漏算 −21｜一页多表**。台班册安拆费用页（jtb 181–184）一页挤 2–7 个独立小表，原逻辑每页只抓第一个 `基价(元)`，每页只核到首表 1 条（21 条只核到 7 条，其中 184 页是 7 条只取 1 条）。
   - 修法：按「定额编号」表头**切段**，逐段独立核算；段内先裁掉「分类」之后的消耗量区，避免材料单价串进费用列。

**铁律（写脚本时就要带）**：
- 标签在但**列数不等** ⇒ 进 `bad_len_pages` 上报，**禁止静默补零**（补零会让残缺列"通过"恒等式）；
- 有基价标签但**两个表头都没有** ⇒ 进 `orphan_pages` 上报，**禁止默认当成子目**；
- 缺标签（如台班册无管理费行）才按 0 计，且**该判断必须由恒等式自身通过来背书**——不是"我觉得没有"就跳。
- 校正后结果：24730 条，与库内原书子目**逐册偏差 0**（24800 − 69 `gd_sup` 补充 − 1 `补991305009`），跑两遍 md5 一致。

**顺带的表式知识**：台班册安拆费用表费用标签印作「机**械**费(元)」而非「机**具**费(元)」，且**无管理费行**。别名要显式列全（`L_MACHINE = ("机具费(元)", "机械费(元)")`），不要指望一套标签走天下。

**容差怎么定（2026-11-28 补）**：这类"基价 = 四项和"的审计，容差**不该拍脑袋取 0.02**，应当由原书自身的算法反推出来。

- 广东实测规律：原书基价 = 人材机管**未舍入中间值**之和，最后才取 2 位；而表头印的四项是**各自先取 2 位**再印。两者只在末位差 1 分，理论最大偏离恰为 **±0.01**（四项各 ±0.005 累积）。
- 全表 24 730 条实测：24 725 条 diff=0，**仅 5 条非零且全部落在 ±0.01**（991304001 / 991305003 / 991305004 / 991305005 / 991305007），逐条用「单价×数量」精确重算证实"原书基价 = 未舍入和取 2 位"：
  `11498.031→11498.03`、`46208.211→46208.21`、`137938.793→137938.79`、`29978.781→29978.78`、`7021.6151→7021.62`。
- 结论：**容差 0.01 即可全通过，且它就是理论边界**；0.02 偏松（会漏掉真错的 1–2 分差），0.00 会误杀 5 条正常印刷差。这 5 条属印刷口径，不改数、不加"原书疑误"标记。
- **必须做的配套**：把贴边界的条目单独记进 `rounding_items`（页码/列/书印基价/四项和/差值）。否则将来某条变成 0.01 时，无法分辨是"印刷精度"还是"真算错了"。只报"100% 通过"等于把这条线索扔掉。
- **通用教训**：容差要能被原书算法解释，并且要留痕。能用"未舍入中间值"重算验证的，就别只靠放宽容差把它盖过去。

**容差要 0 怎么办（2026-11-28 爪哥定调：容差设为 0）** —— 关键不是"调小数字"，而是**换判据**：

- **错误做法**：把 TOL 从 0.01 改成 0，那 5 条立刻报失败，然后人肉逐个"认命"放行。这等于把判据问题伪装成数据缺陷。
- **正确做法**：对"印刷四项相加 ≠ 基价"的列，改用**消耗量重建**——`Σ(单价×数量) + 表头管理费`，`ROUND_HALF_UP` 取 2 位，必须**精确等于**书印基价。这正是原书自己的算法（未舍入中间值相加、最后才取 2 位），所以能做到严格相等：上面 5 条重建结果与书印值一字不差。
- 判据分层：`proven=True` → 记 `rounding_items`（书自洽，印刷口径，不改数）；`proven=False` → 记 `fail_samples`（真问题）。**任何"不等"都必须给证据，不许只记一个"失败"**。
- 注意 Python 的 `round()` 是**银行家舍入**（round-half-even），算钱必须用 `Decimal(...).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`，否则 0 容差下会冒出一批假差异。
- **明细 qty 可能为 NULL**（"含量：xxx"参考行，price=0 无数量），重建时必须跳过而不是当 0 或报错。

**★ 0 容差最容易漏的一环：A6 只证"PDF 自洽"，不证"库里存的就是书上的"**

实测造错：把库内某子目的 `machine` 改掉 1 元，A6 依然报 **100%（20/20）**——因为 A6 全程只读 PDF，用的是自己算的页去验自己算的页，**完全没碰库内值**。这是纯 PDF 侧审计的结构性盲区。

修法：增设 **A6b 闭环比对**——把每列 PDF 印刷的 `base/labor/material/machine/manage` 与库内 `items` 逐字段比对，任何 `>1e-6` 的差异记 drift，直接令 `all_pass=False`。自证：改 1 元后 A6 报 100% 但 A6b 报"漂移 1 处"、退出码 1。

**教训升级**：审计要至少有一环是「书 → 库」的直接比对。只验"书内部自洽"的审计，对"提取写错"和"事后被改"两类问题全盲。

**另一条更隐蔽的坑（同轮抓到）**：平台库根本不存「基价」字段（只有四项费用）。若回灌脚本写成 `base = round(四项和, 2)`，凡原书基价与四项和不完全等的条目都会被**悄悄改写**——广东实测 5 条被改（`11498.03→11498.04`、`46208.21→46208.22`、`137938.79→137938.80`、`29978.78→29978.79`、`7021.62→7021.61`），忠实层即失真，且这种失真在"恒等式 100% 通过"的报告里**完全隐形**（因为基价被改成了四项和，自证必然通过）。
修法：`base` 必须取自 PDF 直接解析的原书值（`*_items_fixed.json` 的 `base` 字段），并加一道**反向门禁 G1b：库内基价 = 原书印刷基价**——不许用四项和自比自证，那是循环论证。
